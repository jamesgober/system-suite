# system-suite v0.4.0 - Extended

**A service reads its configuration, runs its own parts in order, and keeps its background work alive.** v0.4.0 adds configuration with an all-or-nothing reload, metrics, the application's subsystems with a declared start and stop order, supervised workers and timers, health, and the urgent line that tells the whole process to shed load, lock down, or stop.

## What is system-suite?

<strong>system-suite</strong> is the foundation for Rust services: one dependency that brings system facts and a process guard, application paths, environment variables, configuration, logging, metrics, audit records, a registry, signal handling, time, and ids, plus a kernel that starts them in order, supervises background work, reports health and readiness, captures crashes, and shuts everything down in reverse. Each part is its own published library behind its own feature.

```rust
use system_suite::lifecycle::{Deadline, Failure, Link, Position, Subsystem};

struct Http { port: u16 }

impl Subsystem for Http {
    fn name(&self) -> &str { "http" }
    fn position(&self) -> Position { Position::LAST }      // the door opens last, closes first
    fn start(&mut self, link: &Link) -> Result<(), Failure> {
        self.port = link.foundation().config().get_or("http.port", 8080)?;
        Ok(())
    }
    fn stop(&mut self, _deadline: Deadline) -> Result<(), Failure> { Ok(()) }
}

fn main() -> std::process::ExitCode {
    let system = match system_suite::System::builder("site").register(Http { port: 0 }).start() {
        Ok(system) => system,
        Err(error) => return error.report(),
    };
    system.run()
}
```

## What's in 0.4.0

- **Configuration:** one file, `<config dir>/<name>.conf` or the one `<NAME>_CONFIG` names, in config-lib's `conf` format. Every key has a secure default, so the file is optional. The suite's own sections (`[guard]`, `[log]`, `[crash]`, `[metrics]`, `[kernel]`, `[ids]`) are validated and an unknown key is refused, so a typo cannot silently leave a setting at its default. Typed reads with `get`, `require`, and `get_or`, including durations (`"30s"`) and lists.
- **Files only their owner can change:** on Unix a configuration or `.env` file that another user can change is refused (exit 77), checked on the opened file so it cannot be swapped between the check and the read. There is no switch to accept one; the error says to `chmod 640`. A parse error names the line and column and never quotes the text.
- **Reload, all or nothing:** SIGHUP or `System::reload` reads the file again, validates it, and asks every subsystem to prepare its change. Only if all of them agree is the new configuration published and every change committed; otherwise nothing changes and the refusal is logged and counted. Readers see the new version at their next read, for about a nanosecond per read when nothing changed.
- **Subsystems:** the application's parts start after the foundation in a declared order and stop in exactly the reverse. A `stop` that never returns is abandoned at the deadline, the next one is still stopped, and the exit code is 79. Frameworks can stage their own start with `boot()`, `Boot::start`, and `Boot::ready`.
- **Workers and timers:** named threads restarted after a failure with jittered backoff and a restart budget; a critical worker that gives up stops the process. Timers run on one thread that sleeps when nothing is due.
- **The urgent line:** one cache-line word every worker can check for about a nanosecond, plus a mailbox per subsystem that wakes it directly: `Shed`, `Lockdown`, `Draining`, `Stopping`.
- **Health:** every member, subsystem, worker, and the timer thread in one report, as JSON or key-value lines, with readiness and liveness answers; the dump signal (SIGUSR1) writes it to the log. Under systemd, `STATUS=` lines and a `WATCHDOG=1` keep-alive that stops when the system is unhealthy.
- **Metrics:** metrics-lib's registry (process-wide by default), with the kernel's own counters and gauges: boot time, urgent level, worker restarts and failures, subsystem errors, reloads.
- **Opt-in interop and formats:** `log-bridge` sends records from crates that use the `log` facade to the suite's logger; `log-tracing` provides a `tracing` layer that writes through it; `metrics-tracing` adds span-wrapped timing; `config-toml` and `config-noml` read `<name>.toml` and `<name>.noml`. None is in a default build.
- **Model-checked:** the urgent line and the worker heartbeat are tested with loom over every interleaving.

## Not included

JSON and XML configuration, rule-based validation, and JSON and OTLP metrics rendering wait on first-party crates; process metrics are not included. A project that needs one now can add the member crate itself with that feature.

## What's next

`0.5.0` wires audit records, the event registry, process-wide globals, randomness, and secret storage, and resolves secret references (`env:`, `file:`, `vault:`) in the configuration.
