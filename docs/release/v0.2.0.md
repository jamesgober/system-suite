# system-suite v0.2.0 - Design lock

**The public API, written down and approved.** v0.2.0 locked the suite's public API and its boot and shutdown orders before any functional code. Every member's public API was read from source first, so the design wires what the members actually provide. There is still no functional code in this release; the first boot path ships in `0.3.0`.

## What is system-suite?

<strong>system-suite</strong> is the foundation for Rust services: one dependency that brings system facts and a process guard, application paths, environment variables, configuration, logging, metrics, audit records, a registry, signal handling, time, and ids, plus a kernel that starts them in order, supervises background work, reports health and readiness, captures crashes, and shuts everything down in reverse. Each part is its own published library behind its own feature.

## What's in 0.2.0

- `docs/API.md`: the complete public API, items SUI-01 to SUI-30, each with its signature, errors, exit code, estimated cost, examples, and the version it arrives in.
  - Tier 1 is `start!()` (a macro, so the application's own build info is recorded), `System::run`, the typed handles, and `Error::report`.
  - `Builder` and `Boot` (a staged start for frameworks), `Foundation`, one crate-wide `Error` with `sysexits`-style exit codes.
  - Three modules for the kernel's parts: `kernel` (signals to decisions, the urgent line, health, events), `lifecycle` (phases and the `Subsystem` contract with two-phase reload), and `runtime` (supervised workers and timers).
  - A backend-neutral configuration view over config-lib, secret references, `AuditLog`, `Snapshot`, and the member modules.
  - Member features passed through as `<suite feature>-<member feature>`, so a project keeps one dependency line.
- `docs/BOOT-ORDER.md`: 17 boot steps and 10 shutdown steps with the reason for every position, the deadlines, reload, and crash handling. The boot order was revised: the configuration is read before the process guard, and the guard runs before any file or thread exists.
- `dev/PLAN.md`: every open decision answered (the kernel is built here, config-lib is the configuration backend, audit is opt-in, the panic hook is on by default, Windows service control goes through signal-mod), decisions D-008 to D-037, and a dependency register: every third-party crate the members bring is reviewed and recorded instead of counted.
- Requests filed with the members the suite needs changes from: sys-lib, signal-mod, log-io, path-lib, config-lib, and audit-trail.

## What's next

`0.3.0` ships the first boot path: `start!`, `run`, build and instance info, the process guard, paths, environment, logging, signals, crash capture, and the kernel's shutdown order. It waits for sys-lib 0.3 (the boot kit), and for the log-io and path-lib releases requested for crash reports and owner-only files.
