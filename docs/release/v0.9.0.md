# system-suite v0.9.0 - Beta

**The API simplified before 1.0, and the fixes from an independent security review.** A whole service is one line, each handle exists once, each task has one way to do it, and the names are plain words. The review found two high issues, both Windows-only: no configuration, `.env`, or secret file was checked, and a user logging off stopped every service. Both are fixed, with the rest of its findings. Most services need only the version bump; the rest is in [`docs/MIGRATION-0.9.md`](https://github.com/jamesgober/system-suite/blob/main/docs/MIGRATION-0.9.md).

## What is system-suite?

<strong>system-suite</strong> is the foundation for Rust services: one dependency that brings system facts and a process guard, application paths, environment variables, configuration, logging, metrics, audit records, a registry, signal handling, time, ids, randomness, and secret storage, plus a kernel that starts them in order, supervises background work, reports health and readiness, captures crashes, and shuts everything down in reverse.

## One line

```rust
fn main() -> std::process::ExitCode {
    system_suite::run!()
}
```

`run!()` boots every enabled member in order, parks until a stop signal, stops everything in reverse, and returns the exit code. A boot failure is reported (what failed, at which step, and what to do) with the exit code for its kind.

With work of its own, `?` works in `main`:

```rust
fn main() -> Result<std::process::ExitCode, system_suite::Error> {
    let system = system_suite::start!()?;
    let port: u16 = system.config().get_or("http.port", 8080)?;
    system_suite::log::info!(system.log(), "ready", port = port);
    Ok(system.run())
}
```

`Error`'s `{:?}` is now the same report, so an error that leaves `main` reads as one.

## One way each

- `System` dereferences to `Foundation`, which holds every handle once. `system.log()`, `system.config()`, and the rest work as before; the copies on `System` are gone.
- The stop, the health, and the phase are the kernel's: `system.kernel().request_stop(...)`, `.wait_for_stop()`, `.health()`, `.status()`, `.phase()`. The copies on `System` are gone.
- `System::builder(name)` is the one way to get a builder; `Builder::new` is private.
- `Events::register` returns an `EventGuard`: drop it to remove the callback, or call `keep()` to keep it until the shutdown. `register_guard`, `unregister`, and `EventId` are gone.
- A subsystem reaches the kernel as `link.foundation().kernel()`, and a framework as `boot.foundation().kernel()`; `Link::kernel`, `Link::urgent`, `Boot::kernel`, and `Kernel::runtime` were copies and are gone.
- A `HealthReport` prints through `Display`; `write_kv` repeated it and is gone.
- One type per kind of value: `StopReason::exit_code` returns an `ExitCode` like `Error::exit_code`, supervisor stop reasons are a `Cow<'static, str>` like `request_stop`'s, and timer names take the same text as worker names.

## Plain names

- `Foundation::build` is `build_info`.
- The exit codes `DATAERR`, `CANTCREAT`, `IOERR`, `TEMPFAIL`, and `NOPERM` are `DATA_ERROR`, `CANNOT_CREATE`, `IO_ERROR`, `TEMPORARY_FAILURE`, and `NO_PERMISSION`. The values are the same.

## Security

- **Windows file checks.** The configuration, `.env`, `file:` secret, and audit-chain files are checked on the opened file, as on Unix: the owner must be the service's account, SYSTEM, or Administrators, and no other account may change the file (or read it, for a secret). Before, nothing was checked, and `%ProgramData%` lets every local user create files: a standard user could plant `<config dir>\.env` with `CONFIG=` and take over a system service's configuration. A missing system-wide configuration directory is now created owner-only. The check is path-lib 1.2's `file_access`.
- **Logoff.** A Windows service no longer stops when any user logs off. It stops on the service manager's shutdown control, as before.
- **Health reports.** A worker's health reason is the message of its `Failure::new`. An error converted with `?`, whose text can quote a URL with a key in it, shows only that the message is in the log. Every reason is cut to 256 bytes.
- **Reload.** With the secrets member disabled, a reload refuses a secret reference, as the boot does, instead of reading `env:NAME` as the literal value.
- **key-vault 1.2** is required (a nested `Secret::with` panicked on 1.1), and a secret the OS could not page-lock is reported at boot.

## Fixed

- SIGHUP at a terminal with no service manager, or with `reload_signal = false`, stops the process instead of reloading it into a detached process that holds the lock.
- `<NAME>_CONFIG=` in the `.env` file redirects like `CONFIG=`.
- The systemd keep-alive has its own thread, so a slow timer cannot get a healthy service killed.
- An empty secret file says so; crash reports are capped across starts; `Foundation::config()` takes no lock.

What is still open from the review needs member releases (key-vault, audit-trail, signal-mod); each is low and documented as a limit in `docs/SECURITY.md`.

## Documentation

`docs/API.md` is rewritten as a task-oriented tour, and its examples, the README's, and the migration note's run as doctests with every feature, so they cannot drift from the API.

## Members

path-lib 1.2 (file access on Windows) and key-vault 1.2 (nested reads, lock reporting) are required; config-lib 1.3.1 (INI and CONF fixes, a faster CONF parse) is picked up by the existing `1.3` requirement. arc-swap, already in every build with `config` or `secrets`, is now a direct dependency.

## What's next

0.9.x changes the API only to fix it. Before 1.0: two weeks without an API change, James's pre-1.0 review, a second consumer (one gateway already boots on the suite), and the review against real use. The 1.0 readiness note (`dev/READINESS-1.0.md`) lists what is still open and why.
